# Бэкенд и ИИ для «Финика»

Документ под ту мобилку, которая уже есть (запись экрана от 13.09). Мобилку делает один человек,
бэкенд — второй, ИИ-слой — третий. План описывает границу между этими тремя зонами.

## 1. Что уже есть в мобилке (снято с экрана)

Цикл игры недельный. Игрок выбирает росток, имя и доход в неделю, потом раскладывает доход по
четырём статьям и семь дней живёт по плану.

- **Ростки**: Финик (пьёт много воды, +опыт за воду), Кактус Пух (редко ест, дешёвый уход),
  Огонёк (скучает быстрее, +опыт за игры). Черта меняет расходы.
- **Доход в неделю**: 20 (сложно), 40 (обычно), 60 (легко). Меняется в профиле.
- **Статьи плана**: Еда, Вода, Игры, Копилка. Подсказка «Совет 40/30/10/20». Нераспределённый
  остаток показывается отдельно. Копилка «только на мечту».
- **Питомец**: три потребности (Вода, Еда, Игры, в процентах), статус «в порядке · день 3 из 7»,
  реплика питомца, действия Полить / Покормить / Поиграть, каждое списывает из своей статьи
  («3 из 8 · Еда»). Серия входов по дням недели, на седьмой день +5.
- **Лавка**: предметы привязаны к статье, есть скидки (−40 %, −27 %), покупка невозможна, если
  в статье нет монет («Нет монет в статье»).
- **Задания**: пять типов — мини-урок (3 вопроса), недельные («отложи 10 до конца недели»,
  «уложись в план по еде»), привычка («заходи 7 дней подряд»), дневное («купи что-то со скидкой»).
  Каждое с наградой в монетах.
- **Мечта**: цель с ценой (150), накоплено (62), прогноз «при 4 монетах в неделю закроется через
  22 нед.», кнопки «Отложить 5» и «Отложить всё из копилки», график откладываний по неделям и
  текстовый вывод («На третьей неделе почти всё ушло на игры — цель сдвинулась на две недели»).
- **Профиль**: всего заработано, всего отложено, недель с планом, достижения (6), звуки, сброс.

По исходникам (github.com/Bober2244/Finik, Kotlin + Jetpack Compose, коммит «Initial UI without
logic»): в клиенте есть только экраны и навигация. Логики, хранилища и сети нет, все цифры из
`core/model/SampleData.kt`. Модели данных клиента: `PetProfile`, `NeedLevel`, `WeekPlan`,
`PlanEntry`, `CareAction`, `TaskItem`, `QuizQuestion`, `ShopItem`, `SavingsGoal`, `HistoryWeek`,
`WeekLogEntry`, `Badge`, `ReportRow`, `GrowthStage` (5 стадий по опыту 0/100/200/300/400).

## 2. Роль бэкенда: сервер считает игру

Раз правил ещё нет нигде, разумнее положить их на сервер, а клиент сделать тонким: он показывает
состояние и отправляет действия. Причины:

- Другу не надо писать движок экономики на Kotlin, он подключает ViewModel к API и занимается
  экранами и 3D-питомцем.
- Одна реализация правил вместо двух, нечему расходиться.
- Родительский кабинет и ИИ видят те же данные, что и ребёнок.
- Жюри видит настоящую серверную часть, а не хранилище JSON.

Цена: без сети приложение не работает. Для защиты это приемлемо, кэш последнего состояния на
клиенте закрывает мигание при плохой связи.

Альтернатива, если друг хочет считать на клиенте: сервер хранит состояние и раздаёт контент,
`PUT /state` принимает слепок целиком. Решение нужно принять до начала кода, оно меняет форму API.

## 3. Модель данных

- `players`: id, device_id (анонимный вход без регистрации), nickname, weekly_income (20|40|60),
  sounds_enabled, created_at
- `pets`: player_id, sprout (finik|cactus|ogonyok), name, stage (0..3), health,
  water, food, play (0..100), created_at
- `weeks`: id, player_id, number, started_at, income, plan {food, water, play, savings},
  spent {food, water, play}, saved, closed_at, summary_text
- `actions_log`: player_id, week_id, day (1..7), kind (water|feed|play|buy|save|task|event),
  category, amount, item_key, meta, created_at
- `dreams`: player_id, key, title, target, saved, achieved_at
- `task_progress`: player_id, task_key, week_id, progress, done_at, reward_paid
- `events_log`: player_id, event_key, week_id, day, chosen_option, created_at
- `achievements`: player_id, key, unlocked_at
- `parents`: id, email, password_hash; `parent_links`: parent_id, player_id, pairing_code
- `ai_cache`: key, response, created_at

Игровое время: `week.number` и `day` (1..7) ведёт клиент, сервер только записывает. Так не
будет спора, «какой сегодня день», между телефоном и сервером.

## 4. API (префикс /api/v1)

Вход и состояние
- `POST /auth/device` {device_id} → token. Без регистрации, ребёнку ничего вводить не надо.
- `GET /state` → полное состояние: питомец, текущая неделя, мечта, задания, достижения.
- `PUT /state` ← полное состояние с клиента. Сервер валидирует инварианты (план ≤ доход,
  потрачено ≤ план, значения в границах) и сохраняет. Это главный эндпоинт синхронизации:
  клиент шлёт его после каждого действия, дальше остальное работает от сохранённого.
- `POST /week/close` → закрыть неделю: сервер считает итог, пишет точку в историю
  откладываний, генерирует текст вывода (см. ИИ), возвращает новую неделю.

Контент (клиент кэширует, работает офлайн)
- `GET /content/sprouts`, `GET /content/items`, `GET /content/tasks`, `GET /content/events`,
  `GET /content/dreams`, `GET /content/lessons`

События (новое для клиента, минимально)
- `GET /events/today` → событие дня или null: скидка в лавке, подорожание корма, росток
  приболел (нужны витамины), «сообщение от незнакомца: переведи 10 монет и получишь 30».
- `POST /events/{id}/choose` {option} → последствия и реплика питомца.

Родитель
- `POST /parent/register`, `POST /parent/login`, `POST /parent/link` {pairing_code}
- `GET /parent/child/{id}` → недели, планы, факт, накопления, задания, выводы ИИ.
- `POST /parent/child/{id}/bonus` {amount, reason} → монеты ребёнку за реальное дело.

ИИ (все вызовы через сервер, ключ только на сервере)
- `POST /ai/pet-remark` — реплика питомца по состоянию.
- `POST /ai/week-summary` — вывод по итогам недели человеческим языком.
- `POST /ai/lesson` {topic, age} — мини-урок на 3 вопроса.
- `GET /ai/word-of-day` — «слово дня» простыми словами.
- `POST /ai/dream-plan` {dream, income, saved} — разбить мечту на шаги.
- `POST /ai/diary` — запись в дневник ростка по журналу дня.
- `POST /ai/chat` {text} — вопрос питомцу, с фильтром тем и лимитом в день.
- `GET /parent/child/{id}/report` — отчёт родителю за неделю.

## 5. ИИ-слой (зона третьего участника)

- Единая обёртка над провайдером: YandexGPT или GigaChat, переключение переменной окружения,
  таймаут 8 с, при любой ошибке — заготовленная фраза, клиент ошибку не видит.
- Персона ростка: имя, вид, черта, состояние, план и факт недели, мечта. Правила: 1–3 коротких
  предложения, на «ты», без нотаций, ничего вне игры и финансов, не просить личных данных.
- Кэш ответов по хешу контекста, чтобы не платить дважды за одно и то же.
- Стоп-лист на входе (мат, взрослые темы, реквизиты). При срабатывании питомец мягко
  переводит тему, никаких «обращений в полицию».

## 6. Идеи из списка Руслана: что берём

Берём в первую очередь (дёшево и ложится на текущий экран)
- События: скидки, подорожание, болезнь ростка, сообщение мошенника. Обучающий эффект сильнее
  всего именно здесь.
- Стадии роста ростка. Это главная награда, видимая на экране «Питомец».
- Слово дня. Одна LLM-функция, отдельная карточка на экране заданий.
- Дневник ростка по итогам дня. Дети такое перечитывают, ИИ пишет сам.
- Разбить мечту на шаги. Одна кнопка на экране «Мечта».
- Вклад под процент как расширение копилки. Один рычаг, одна формула.
- Викторина «сколько яблок стоит велосипед». Генерируется ИИ, награда монетами.
- Домашние дела за монеты — это уже «Задания», расширяем список.

Берём, если останется время
- Грамота в PDF за мечту. Приятно на защите, полдня работы.
- Благотворительность: пожертвовать монеты ради настроения ростка.
- Вопросы «родителям», которых играет ИИ.

Не берём на хакатон
- Мультиплеер, соцсеть, выставки, соревнования: серверная сложность и ноль обучающего эффекта
  за оставшееся время.
- Казино, биржа, ставки, донат за зелье: жюри от города это точно не оценит в детском
  приложении по финансовой грамотности.
- Опека забирает щенка, звонок в полицию: слишком жёстко для 7–12 лет. Росток вянет и грустит,
  этого достаточно.
- Распознавание речи, деревня/город, несколько рассказчиков: большой объём ради небольшого
  эффекта.

## 7. Порядок работы бэкенда

1. Каркас: FastAPI, PostgreSQL, Docker, вход по device_id, `PUT /state` и `GET /state`.
   Уже на этом шаге мобилка может синхронизироваться.
2. Контент-эндпоинты из JSON-файлов. Мобилка переключает справочники на сервер.
3. Закрытие недели и история откладываний, родитель и привязка.
4. События.
5. Точки для ИИ с заглушками: они возвращают заготовленные фразы, третий участник заменяет
   внутренности, не трогая контракт.
6. Родительская веб-страница, если время есть.

## 8. Что нужно от команды

- Исходники мобилки, чтобы снять точную структуру состояния для `PUT /state`.
- Дата и время сдачи.
- Ключи YandexGPT или GigaChat, либо решение работать на заглушках до защиты.
