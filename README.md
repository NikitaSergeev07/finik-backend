# Финик — бэкенд

Серверная часть детского приложения по финансовой грамотности. Сервер считает правила игры,
мобильный клиент показывает состояние и отправляет действия. План и разбор идей — в PLAN.md.

## Запуск локально

Нужны PostgreSQL 15+ и uv.

```bash
brew services start postgresql@15
createdb finik && createdb finik_test
cp .env.example .env
uv sync --all-groups
make migrate
make seed
make dev
```

Документация API: http://localhost:8000/docs

## Команды

| Команда | Что делает |
|---|---|
| `make dev` | API с автоперезагрузкой на порту 8000 |
| `make migrate` | применить миграции |
| `make revision m="описание"` | создать миграцию по изменённым моделям |
| `make seed` | заполнить справочники: лавка, задания, уроки, достижения, события |
| `make test` | все тесты на базе finik_test |
| `make lint` | ruff: проверка и формат |

Через Docker: `docker compose up --build`, миграции применятся сами.

## Архитектура

Четыре слоя, зависимости направлены внутрь: api → application → domain ← infrastructure.

```
src/
├── domain/          правила игры на чистом Python, без FastAPI и SQLAlchemy
│   ├── enums.py     виды ростков, статьи плана, настроение
│   ├── rules.py     все числа баланса в одном месте
│   ├── entities.py  Player, Pet, Week, PlanEntry, Goal, LogEntry
│   └── services/    planning, care, growth, persona, safety, words
├── application/     сценарии и порты
│   ├── ports.py     протоколы репозиториев, единицы работы и LLM
│   ├── dto.py       что сценарии отдают наружу
│   └── use_cases/   onboarding, gameplay, shop, tasks, events, ai
├── infrastructure/  реализация портов
│   ├── db/          engine, ORM-модели, репозитории, mappers, uow
│   └── ai/          клиент GigaChat и шлюз с заготовками
├── api/             FastAPI: зависимости, схемы, роутеры v1
└── main.py          сборка приложения и обработчик ошибок
```

Правила лежат в `domain/services` и тестируются без базы (`tests/domain`). Сценарии в
`application/use_cases` открывают одну транзакцию, вызывают правила, пишут журнал и коммитят.
Репозитории переводят строки базы в сущности домена и обратно через `mappers.py`; ORM-модели
наружу не выходят. Ошибки домена наследуют `AppError` и превращаются в ответ
`{"error": {"code", "message"}}` одним обработчиком.

## Цикл игры

Игровая неделя из семи дней. Доход приходит в начале недели свободными монетами, ребёнок
раскладывает их по статьям: Еда, Вода, Игры, Копилка. Уход за ростком списывает монеты из своей
статьи. Если в статье еды или воды пусто, монеты берутся из копилки, и это перерасход. День
завершается явным действием: потребности убывают, начисляется опыт. Если потребность упала
до нуля, росток вянет: −20 опыта и откат на стадию назад, если уже не семечко (не опека).
На седьмом дне неделя закрывается: остаток копилки уходит в мечту и растёт на 5% (дробь
отбрасывается), остатки статей возвращаются, приходит новый доход. Редкий огонёк (SPARK)
получает 1–2 монеты кэшбэка с остатка игр. Цены лавки и цели заданий растут с номером
недели (таблица множителей в `domain/rules.py`, потолок цен 1.5, заданий 2.0).

Игровые: `players`, `pets`, `weeks`, `plan_entries`, `goals`, `action_log`, `purchases`,

## Контент

Справочники лежат кодом в `src/infrastructure/content/catalog.py` и заливаются командой
`make seed`. Повторный запуск обновляет строки, не плодя дублей. В сиде не меньше 8 товаров
лавки двух типов (нужда / желание) и не меньше 6 заданий по темам план / накопление / покупки.
Каталог мечт — три цели в `domain/rules.py` (`GET /content/goals`). Задания оцениваются по фактам
недели в `domain/services/tasks.py`: урок по верным ответам, накопление по вкладам и копилке,
привычка по дням с уходом, покупка со скидкой по журналу покупок.

## События

Одно событие на игровой день. Выбор детерминирован хешем от игрока, недели и дня.
В профиле можно поставить `event_mode`: `random` (как сейчас) или `escalating` (чаще
события с большим `min_week`). Каталог: `sale_day`, `price_rise`, `sick`, `scam_message`,
`charity`, `crisis`, `new_food`, `guests`, `vaccine`, `pyramid`.

`effects`: `coins` — свободные монеты; `pay` — сначала свободные, иначе копилка;
`cost` — статья плана; `need`; `xp`; `note`; `price_delta` — надбавка к ценам лавки
до конца недели; `sale_percent` — скидка витрины до конца недели; `vaccinate` — недели
без события болезни; `unlock_shop` — товар появляется у этого игрока. В минус уйти нельзя.

`price_rise` поднимает еду на +2 до закрытия недели. `sale_day` даёт −30% на витрине.
Прививка (`vaccine`) за 3 монеты закрывает `sick` на 4 недели включая текущую.

## GigaChat

Клиент в `src/infrastructure/ai/gigachat.py`. Схема из документации Сбера: ключ авторизации
обменивается на токен доступа через `POST /api/v2/oauth` (живёт 30 минут, кэшируется),
запросы идут на `https://api.giga.chat/v1` с Bearer-токеном.

Как получить ключ: developers.sber.ru → Studio → проект GigaChat API → Настройки API →
Получить ключ. Ключ показывается один раз, в кабинете не хранится. Скопировать в `backend/.env`:

```
FINIK_GIGACHAT_AUTH_KEY=<Authorization Key>
```

Проверка: `make ai-check` печатает список моделей и одну реплику ростка. Пустой ключ
выключает ИИ, сервер работает на заготовленных фразах. Модель по умолчанию
`GigaChat-3-Lightning` (бывший Lite, 250 млн токенов на бесплатном тарифе), умнее и дороже
`GigaChat-3-Pro` и `GigaChat-3-Ultra`. Таймаут 8 секунд: если модель не успела, клиент
получает заготовку и поле `source: fallback`. Повтор того же контекста берётся из кэша
(`source: cache`).

Точки `/api/v1/ai/*` всегда отвечают 200 (кроме «неделя ещё не закрыта» на итог). В ответе
`source`: `llm`, `cache` или `fallback`. Реплика на главном экране без сети модели — поле
`pet.mood_note` в `GET /state`. Цифры плана мечты считает сервер (в том числе «урезать игры на 2»), модель пишет только совет.
Чат: стоплист (мат, ссылки, номера карт) и 12 реплик на игровой день. Слово дня кэшируется
на календарный день без привязки к игроку. История ростка — `GET /ai/origin`, кэш по виду
и имени. Викторина лавки: сервер считает верный ответ по текущим (уже умноженным) ценам.

TLS: у Сбера в цепочке корневой сертификат Минцифры, он лежит в `certs/` и подставляется
клиенту через `FINIK_GIGACHAT_CA_BUNDLE`. Отключать проверку не нужно.

## Подключение мобилки

Сервер на машине разработчика слушает `0.0.0.0:8000`. Адрес из эмулятора Android:
`http://10.0.2.2:8000`, с физического телефона в той же сети: `http://<ip-компьютера>:8000`.
Android по умолчанию запрещает HTTP без TLS, для отладочной сборки нужно разрешить:
`android:usesCleartextTraffic="true"` в манифесте debug-варианта или network security config.

Порядок вызовов с клиента:

1. `POST /api/v1/auth/device` с `device_id` (например `Settings.Secure.ANDROID_ID`) → токен.
   Ответ содержит `has_pet`: если false, показать знакомство.
2. `GET /api/v1/content/goals` — три мечты. На экране «Имя» выбирают вид, цвет и доход,
   затем мечту; `POST /api/v1/pet` с `goal_slug` и `look_variant`.
3. Дальше каждый экран читает `GET /api/v1/state`, а действия зовут свои эндпоинты и
   получают в ответ обновлённое состояние, так что перечитывать его отдельно не нужно.
   План можно менять, пока не вызван `POST /api/v1/plan/confirm`.

Все ответы повторяют модели `core/model` мобилки: `PetOut` ↔ `PetProfile`, `PlanEntryOut` ↔
`PlanEntry`, `TaskOut` ↔ `TaskItem`, `ShopItemOut` ↔ `ShopItem`, `GoalOut` ↔ `SavingsGoal`,
`HistoryWeekOut` ↔ `HistoryWeek`, `ReportRowOut` ↔ `ReportRow`, `BadgeOut` ↔ `Badge`.
Ошибки приходят как `{"error": {"code", "message"}}`, `message` можно показывать ребёнку как есть.
